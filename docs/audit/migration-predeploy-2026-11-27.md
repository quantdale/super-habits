The audit started at `acf859f2` and used disposable PostgreSQL 17.12 with a minimal Supabase Auth and role shim plus local client tests. Git identified five pending migrations ending in `20261123140000_add_reward_snapshot_scope.sql` from #278. The driver's forward-only policy keeps all five merged migration files byte-identical.

## Owner decisions before deployment

1. **Protect historical snapshots before provenance cleanup.** The local fixture published two snapshots before the journal existed and staged a third. `20261019162537` journaled the current head. `20261020090000` then deleted the previous published snapshot and its chunks along with unjournaled staging. A later migration cannot recover those bytes. If the cleanup is still pending, establish a restorable database snapshot and decide how to retain potentially published history before running it. If it already ran, inspect backups for any needed recovery. A lower sequence alone cannot distinguish publication from staging. Confirm the live migration ledger and preservation policy before applying the chain.
2. **Coordinate the client rollout.** Apply pending migrations in timestamp order, ending with the forward fix. Current clients pause backup and retain their outbox on the predecessor schema. Older generation-aware builds pause cloud writes against the final capability. A Scope 9 client refuses to restore a Scope 10 head, and pre-generation clients can still read mutable data without seeing newer immutable content. Decide how to communicate or enforce the client upgrade before exposing Scope 10. The obsolete reservation and publication RPCs are deliberately retired.
3. **Confirm the mutable saved-meal index policy.** The earlier `uq_saved_meals_owner_food_name` index independently rejected the same names on local PostgreSQL with Unicode case folding. Immutable publication now accepts both, while mutable sync can still fail on that index. Replacing a potentially deployed index requires a forward migration, a preflight under the target fold, and a locking plan.
4. **Decide the account erasure procedure.** An admin deletion of a fixture Auth user with published history failed on `backup_generation_publication_user_id_snapshot_id_fkey`. Decide and test the approved erasure order for journal, head, generation data, and the Auth user.
