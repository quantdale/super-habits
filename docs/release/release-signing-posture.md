# Release signing and build-posture record (unproven release posture)

**Status: UNPROVEN RELEASE POSTURE. There is no store-buildable artifact in this
repository, and nothing here should be read as one.**

Companion to `app-store-readiness.md`, `version-build-consistency.md`, and
`submission-package.md` (R10/R15). This file records what the release build path
actually does today, measured from the generated Android project on
2026-09-30, so a reader asking "can we ship this?" gets the true answer instead
of an assumption. Every statement below is a `[OWNER ACTION]`-free reading of
tracked configuration plus the generated tree; nothing here was certified by a
store submission, and no keystore, credential, tag, or submission exists.

Guard: `tests/releaseBuildPosture.test.ts` re-reads every source cited below, so
a change to signing, identity, or minification fails the gate instead of quietly
making this file wrong.

## 1. The only executable Android release path is debug-signed

The generated release build type signs with the **debug keystore**:

```gradle
// android/app/build.gradle (generated by `expo prebuild`; NOT tracked)
signingConfigs {
    debug { storeFile file('debug.keystore'); storePassword 'android'; … }
}
buildTypes {
    release { signingConfig signingConfigs.debug }
}
```

Consequences, stated plainly:

- An APK produced by `npm run qa:native:provision` (which runs
  `app:assembleRelease`) or by any local Gradle release task is signed with the
  shared, publicly known Android debug key. It is **not** uploadable to Play,
  which rejects debug-signed artifacts.
- No production keystore, keystore password, key alias, or
  `credentials.json` exists in this repository or in tracked configuration, by
  design: producing a production signing key is an owner action with custody
  consequences, and a locally generated key that is not the owner's is worse
  than none — it would let a QA build look store-buildable.
- iOS signing is equally unproven: no `ios/` tree is generated on the Windows
  host, and no distribution certificate, provisioning profile, or App Store
  Connect key is present. iOS certification evidence comes from the
  EAS-hosted `e2e-test` lane only (`.eas/workflows/native-e2e.yml`), which
  builds an unsigned simulator app.

**Exact resume action for the owner:** create the production upload key
(`keytool -genkeypair -v -keystore superhabits-upload.jks -keyalg RSA -keysize
2048 -validity 10000 -alias upload`), store it and its credentials in the
owner-controlled secret store (never in this repository), then add a
`release` signing config that reads the key path and the four credentials from
Gradle properties supplied at build time. Verify with
`apksigner verify --print-certs <apk>` that the artifact's certificate SHA-256
is the upload key's, not the debug key's, before any Play upload.

## 2. The E2E and store builds share one application identity and version code

| Property                             | Value                    | Source                                 |
| ------------------------------------ | ------------------------ | -------------------------------------- |
| Android `applicationId`              | `com.dale16.superhabits` | `app.json` `expo.android.package`      |
| Android `versionCode`                | `1`                      | `app.json` `expo.android.versionCode`  |
| iOS bundle identifier                | `com.dale16.superhabits` | `app.json` `expo.ios.bundleIdentifier` |
| iOS `buildNumber`                    | `1`                      | `app.json` `expo.ios.buildNumber`      |
| `applicationIdSuffix`                | **absent**               | generated `build.gradle` has no suffix |
| EAS `cli.appVersionSource`           | `remote`                 | `eas.json`                             |
| EAS `build.production.autoIncrement` | `true`                   | `eas.json`                             |

There is **no `applicationIdSuffix`**, so the credential-free native E2E APK, the
preview APK, and a future store build all share one application id and one
`versionCode`. That is a deliberate trade with a real consequence: an E2E build
and a store build **cannot coexist on one device**, and a store build would have
to _upgrade over_ an installed E2E build (or the user uninstalls first). The
E2E lane installs with `adb install -r -d -g`, so it overwrites whatever is
there.

**Exact resume action for the owner:** decide the identity posture explicitly —
either keep the shared id and document that Play must uninstall the E2E build
before a real install, or add an E2E-only `applicationIdSuffix` (for example
`com.dale16.superhabits.e2e`) in tracked configuration so the two can coexist.
Whichever is chosen, record it here and re-run the native E2E lane, because the
lane's identity checks pin `com.dale16.superhabits`.

## 3. Release builds are neither shrunk nor obfuscated

```gradle
def enableShrinkResources = findProperty('android.enableShrinkResourcesInReleaseBuilds') ?: 'false'
def enableMinifyInReleaseBuilds = (findProperty('android.enableMinifyInReleaseBuilds') ?: false).toBoolean()
release {
    shrinkResources enableShrinkResources
    minifyEnabled enableMinifyInReleaseBuilds
}
```

Both default to **false** and neither property is set in tracked configuration,
so a release build ships unminified and unshrunk: larger download, larger memory
footprint, and readable stack traces — which is good for a first release and
wrong for a long-lived one.

**Exact resume action for the owner:** after a store-signed build exists, decide
whether to enable R8 (`android.enableMinifyInReleaseBuilds=true` plus
`android.enableShrinkResourcesInReleaseBuilds=true`), then re-run the full native
E2E battery against the minified build — Hermes bytecode and reflection-based
code paths are exactly what minification breaks, so the lane is the proof, not
the build's exit code.

## 4. Test-only seams must not ship

`EXPO_PUBLIC_HABIT_REMINDER_E2E_TEST` is the native test seam the E2E lane sets
(`eas.json` `build.e2e-test.env`, and `qa-native-provision.mjs` for the local
APK). It is inlined into the JavaScript bundle like any `EXPO_PUBLIC_*` value,
so a release build carrying it would ship the test seam to users.

`scripts/release-profile-guard.mjs` (run by `npm run release:profiles:guard`,
and by `qa:fast`) rejects any `eas.json` build profile other than `e2e-test`
that sets it, and rejects a release-candidate profile that sets it through
`app.json` instead. This record and the guard are the pair: the guard is the
enforcement, this section is the reason.

## 5. What is deliberately NOT recorded here

- No APK/AAB hash, build ID, or store submission ID: none exists.
- No production keystore path, alias, or credential reference.
- No claim that any build in this repository is installable from Play or
  TestFlight.
