## Purpose

Defines the deterministic-snapshot contract for Frontend V3 W15: what is
snapshotted, how determinism is achieved, how a baseline change is approved, and
what stability and sensitivity evidence the suite must produce. The suite
asserts rendered appearance only; it changes no product behaviour and replaces
no functional test.

## ADDED Requirements

### Requirement: The suite uses a curated, risk-weighted baseline set

The visual-regression suite SHALL snapshot an intentional set of
surface/state/viewport/theme combinations chosen to cover every distinct UI
anatomy, and SHALL NOT attempt an exhaustive cross-product of every surface,
state, width and theme.

#### Scenario: Every anatomy class is represented

- **WHEN** the curated suite is generated
- **THEN** the global shell, each primary destination, a list/row anatomy, an overlay, at least one empty state, at least one error/loading state, and each W12/W13 secondary surface are represented
- **AND** at least one dark-theme snapshot exists per major surface class
- **AND** each snapshot has a recorded surface, fixture, viewport, theme and rationale

### Requirement: Snapshots are deterministic across runs

Each snapshot SHALL be captured from a freshly reset and seeded database, under
an installed fixed clock, after explicit font readiness, with reduced motion
emulated and animations disabled, at an explicitly set viewport and device
scale factor, and without any external network dependency.

#### Scenario: Two independent runs agree

- **GIVEN** an unchanged source tree and build
- **WHEN** the suite is executed twice in independent fresh browser contexts
- **THEN** both runs pass against the same baselines with zero diffs
- **AND** no baseline is rewritten automatically by either run

#### Scenario: A state change fails rather than becoming a baseline

- **GIVEN** a snapshot whose required semantic element is absent
- **WHEN** the suite runs
- **THEN** the test fails before capturing
- **AND** no new baseline is written in CI

### Requirement: Masking is limited and justified

The suite SHALL mask only values that are nondeterministic facts unrelated to
the product contract, and SHALL record a reason for each masked region.

#### Scenario: Product content is never masked

- **WHEN** a snapshot defines a mask
- **THEN** the manifest records why that region is nondeterministic
- **AND** no snapshot masks a title, a count, a primary action, or an entire section

### Requirement: Baseline changes are reviewed, not automatic

A baseline update SHALL be a deliberate, recorded act: generated outside CI,
inspected against the previous image and the diff, justified by an intentional
design change with its source revision, and never produced by loosening a
comparison threshold.

#### Scenario: An unexplained visual shift is rejected

- **GIVEN** a snapshot that differs from its baseline
- **WHEN** the difference is not an intentional, reviewed design change
- **THEN** the baseline is not updated
- **AND** the difference is investigated as a defect

#### Scenario: A deliberate design change is recorded

- **GIVEN** an intentional visual change
- **WHEN** its baseline is updated
- **THEN** the update is generated by the dedicated developer command
- **AND** the change is recorded with its source revision in the baseline manifest
- **AND** no comparison threshold was loosened

### Requirement: The suite proves stability and sensitivity

The suite SHALL demonstrate both that unchanged baselines pass repeatedly and
that a real visual change fails, so a green result is evidence rather than an
assumption.

#### Scenario: Negative sensitivity is demonstrated

- **GIVEN** a controlled perturbation to a snapshotted style in an isolated working tree
- **WHEN** the affected snapshot runs
- **THEN** it fails with a diff artifact
- **AND** the perturbation is reverted before publication

### Requirement: The suite is registered in the standard battery without silent skipping

The suite SHALL run as a registered project in the repository's standard test
battery and SHALL NOT be gated in a way that lets it skip silently.

#### Scenario: The lane executes explicitly

- **WHEN** the standard battery runs
- **THEN** the visual-regression spec executes as its own lane
- **AND** a skipped run is distinguishable from a passing one in the report
