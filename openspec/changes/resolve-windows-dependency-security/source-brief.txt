# 6. Phase D — identify remediation options

Enumerate realistic fixes before editing.

Consider in this order:

### Option 1 — upgrade the direct parent safely

If a patch/minor parent upgrade removes the vulnerable dependency or brings in a patched `node-forge`, prefer it.

### Option 2 — compatible `node-forge` override

If `node-forge` has a fixed version compatible with all parents, consider an npm override.

Before applying an override, verify:

- API compatibility
- parent version range
- package usage
- lockfile resolution
- affected tests

Do not use an override merely because npm accepts it.

### Option 3 — update a dependency family

If a parent package needs a compatible minor/patch update, perform the smallest safe update.

### Option 4 — remove unused dependency path

If the chain is genuinely unused and removable without reducing functionality, remove it.

### Option 5 — narrowly documented exemption

This is LAST RESORT.

Only consider it if all of the following are proven:

1. no safe patched dependency exists;
2. no safe parent upgrade exists;
3. the dependency is demonstrably not runtime-reachable in shipped artifacts;
4. the vulnerability's affected API is not used;
5. the classification is reproducible;
6. the exemption can name exact package/path/advisory;
7. it has a date, rationale, and removal condition;
8. it does not broadly exempt `node-forge`, all highs, or an entire dependency family.

If these conditions are not met, do not add an exemption.

Never change the audit policy from “new high/critical fails” to a weaker global policy.
